# Installed mod static audit — 2026-08-21

## Scope

This audit was performed without launching Civilization VI. The Steam Workshop directory contained 25 mod manifests. Eleven directories had just been added relative to the prior 20-mod inventory, while six older subscriptions were no longer present.

The audit traces manifest-loaded gameplay scripts and searches for direct GameCore mutation controlled by client-local identity or UI/Lua events. It also reviews UI-only mods for cross-context bridges and direct operation requests.

## Findings

### Critical: Multiplayer Helper 1.6.7 (`2357532056`)

Gameplay file: `data/MP_helper.lua`

The gameplay script exports its `LuaEvents` object through `ExposedMembers.LuaEvents`. UI scripts retrieve that object and emit events directly into gameplay context. Several handlers mutate GameCore without `UI.RequestPlayerOperation` or another synchronized command:

- `UICPLPlayerDrop` calls `UnitManager.ChangeMovesRemaining(unit, -99)` for every unit belonging to the disconnected player.
- `UICPLPlayerConnect` restores movements from a process-local `Drop_Data` table.
- `UISuddenDeathTimeExpireAI` destroys every unit and city belonging to the selected player.
- `UISuddenDeathSavetime` writes `Game:SetProperty("MPH_SD_TIME_LEFT", timeleft)`.

The disconnect UI invokes its bridge from `Events.MultiplayerPrePlayerDisconnected`; connection handling and process-local timing can differ between clients. The sudden-death UI attempts to distribute commands through chat messages, but each receiving UI still invokes a local Lua event and direct mutation. Delivery, ordering, UI load state, and local timers can differ.

This is a direct mechanism for large simulation divergence. A player disconnect/reconnect is the clearest natural trigger: one client can freeze or restore unit movement using local `Drop_Data` while another executes a different sequence or lacks the saved table.

Additional concerns:

- `OnGameTurnStarted` consumes `Game.GetRandNum` for logging; this is safe only if every client executes the handler exactly once in the same order.
- The same handler records `os.date`, but the wall-clock value is currently printed rather than written to gameplay state.
- `NoMoreStack` directly selects missing technologies/civics for every player. It is attached to a deterministic GameEvent, but bypasses player operations and increases the consequence of event-order differences.
- The mod contains multiple UI-side `math.random` calls used for staging/draft configuration. Those values must be broadcast and applied identically to avoid mismatched setup state.

### Critical: Tech Civic Progress Plus (`2604740398`)

Gameplay file: `CheckOverflow.lua`

This ostensibly UI-only information mod installs an `AddGameplayScripts` component. Its active technology-overflow calculation:

1. chooses `Players[Game.GetLocalPlayer()]`;
2. repeatedly calls `SetResearchProgress` on an unfinished technology;
3. recursively probes turns-to-research; and
4. attempts to restore the original progress afterward.

Only the client that locally owns the player executes the `ResearchCompleted` callback path. The UI tooltip also calls the exposed gameplay function when local research progress changes. Other clients do not reproduce those temporary GameCore writes.

Restoring the saved numeric value reduces the chance of permanent divergence, but does not make the design safe: an exception, recursion failure, rounding difference, re-entrant event, or side effect before restoration can leave state changed. It also exposes intermediate states to any callback or hash checkpoint that occurs during calculation. A tooltip must never calculate presentation data by temporarily rewriting synchronized research state.

The correct design is a read-only overflow calculation. If the engine does not expose sufficient read APIs, the mod should omit the estimate rather than mutate and restore live GameCore state.

## Recommended source fixes

1. Multiplayer Helper must replace every UI-event direct mutation with a synchronized, authoritative command path. Drop/reconnect state must be serialized and keyed by explicit player/unit IDs, not retained only in a client-local Lua table. Wall-clock/UI timer decisions must be made by one authority and transmitted as ordered commands.
2. Tech Civic Progress Plus must make overflow calculation read-only. Remove every temporary `SetResearchProgress`, `SetCulturalProgress`, and `SetProgressingCivic` operation from tooltip calculation.
3. Quick Deals must keep its cache in UI-local memory and remove synchronized `Player:SetProperty` writes.

Suppressing Civ VI's resync is not a safe repair; these upstream divergent mutations must be eliminated.
